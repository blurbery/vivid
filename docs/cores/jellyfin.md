<h1 align="center">Jellyfin server core</h1>
<p align="center"><a href="../README.md">Documentation</a> · <a href="vivid.md">Vivid core</a> · <a href="../server-connections.md">Server connections</a></p>

---

Jellyfin has its own server core. Its provider card opens Vivid's existing server and username/password forms on iPhone, iPad and Apple TV, with [Quick Connect](#quick-connect) as a second way to sign in. The connection supplies metadata and playable sources to Vivid's shared player; it does not use Silo Protocol V3 or the Emby adapter.

## Ownership and authentication

`JellyfinProvider.swift` owns Jellyfin discovery, authenticated transport and catalogue mapping. `JellyfinPlayback.swift` owns playback negotiation and reporting. `JellyfinDownloads.swift` and `JellyfinLocalPreferences.swift` keep download records and client preferences separate from other providers. Shared Vivid code selects the provider and presents its results. Silo and Emby wire implementations remain unchanged.

Server identities use a `jellyfin:` prefix. Native user IDs and access tokens remain scoped to that server account in Keychain. Requests capture their account identity and reject results after a session switch. Authentication uses Jellyfin's MediaBrowser authorisation header. Credentials are not placed in generated image, subtitle or media URLs, and API redirects are rejected. Custom server base paths are preserved without adding `/emby` or `/jellyfin`.

### Quick Connect

Accounts without a password, such as OIDC-only users, sign in with [Jellyfin Quick Connect](https://jellyfin.org/docs/general/server/quick-connect/). When the server reports Quick Connect turned on, the first-run sign-in form shows Use Quick Connect on iPhone, iPad and Apple TV. Add Profile, Sign In and Update Login on a Jellyfin profile offer it too; there the server is checked when the code is requested. Vivid shows the six-digit code Jellyfin returns, and the user approves it from a signed-in Jellyfin app under Settings > Quick Connect. Vivid asks every five seconds whether the code has been approved, then exchanges it for an ordinary session, saved like a password sign-in. The username comes from the server, and Update Login still refuses a code approved by a different Jellyfin user. A temporary failure while waiting (no connection, a timeout, rate limiting or a server error) keeps waiting, and exchanging the approved code is tried up to three times. A code Jellyfin no longer knows, or ten minutes without approval, offers a new code. Once the code is approved, the code screen can't be cancelled or replaced with a new code while the session is saved. On the first-run sign-in form, a server with Quick Connect turned off, or without the route (older than Jellyfin 10.8), doesn't show the choice. The profile editors offer it on every Jellyfin profile and show "Quick Connect isn’t turned on for this Jellyfin server" when the code is requested. An address that isn't Jellyfin 10.8 or later (no route, or an answer other than `true` or `false`) shows "This server doesn’t offer Quick Connect. Check that the address is your Jellyfin server." instead. Changing the address clears an earlier code or message. Jellyfin 10.8 starts a request with `GET`; newer servers use `POST`, and Vivid falls back to `GET` on a 404 or 405. The approval request goes to the user's own Jellyfin server only, under the same device ID as password sign-in.

Quick Connect was checked on the iPad simulator against the public Jellyfin 12.2 demo server: first-run sign-in and Sign In on a signed-out profile both opened Home, and Update Login offered the choice. Those codes were approved through Jellyfin's `QuickConnect/Authorize` API rather than its apps. Apple TV builds, but its Quick Connect screens and focus haven't been run. The Jellyfin 10.8 `GET` fallback and the expired and turned-off paths are covered by request tests only.

## API mapping

The core follows the [official Jellyfin API specification](https://api.jellyfin.org/openapi/jellyfin-openapi-stable.json).

| Vivid operation | Jellyfin endpoint |
|---|---|
| Server discovery | `GET /System/Info/Public` |
| Login / logout | `POST /Users/AuthenticateByName`, `POST /Sessions/Logout` |
| Quick Connect | `GET /QuickConnect/Enabled`, `POST /QuickConnect/Initiate`, `GET /QuickConnect/Connect`, `POST /Users/AuthenticateWithQuickConnect` |
| Libraries | `GET /UserViews` |
| Browse, search, favourites and history lists | `GET /Items` with native filters |
| Item details | `GET /Items/{id}` |
| Home rows | `GET /UserItems/Resume`, `/Shows/NextUp`, `/Items/Latest` |
| Seasons / episodes | `GET /Shows/{id}/Seasons`, `/Shows/{id}/Episodes` |
| Filters / similar titles | `GET /Items/Filters`, `/Items/{id}/Similar` |
| Artwork | `GET /Items/{id}/Images/{type}` |
| Playback negotiation | `POST /Items/{id}/PlaybackInfo` |
| Original stream and original-file downloads | `GET /Videos/{id}/stream` |
| Smaller downloads | `GET /Videos/{id}/stream.mp4` |
| Subtitle files beside the media | `GET /Videos/{id}/{sourceId}/Subtitles/{index}/Stream.{format}` |
| Session reporting | `POST /Sessions/Playing`, `/Sessions/Playing/Ping`, `/Sessions/Playing/Progress`, `/Sessions/Playing/Stopped` |
| Watched / favourite changes | `POST` or `DELETE /UserPlayedItems/{id}`, `/UserFavoriteItems/{id}` |
| Offline progress | `POST /Sessions/Playing/Stopped` |
| Downloaded items' watched state | `GET /Items?UserId={userId}&Ids={ids}` |

Jellyfin 12 moved several user-scoped routes. An HTTP 404 on a mapped route retries its corresponding older Jellyfin route under `/Users/{userId}` once. This also includes missing-item 404 responses; the client does not distinguish a missing route from a missing resource. When the older route then succeeds, the server is remembered for the rest of the launch and later mapped requests use the older route directly. A missing item fails on both routes and is not remembered. If a remembered older route returns 404, the current route is retried and the preference is cleared. Authentication failures do not trigger fallback, and no fallback selects another provider. Older Jellyfin server versions still need live verification.

## Playback and limits

Jellyfin maps source IDs, media streams, chapters and tick-based progress into Vivid's models. PlaybackInfo supplies direct-play or transcoded sources. Its device profile comes from the shared [decode capabilities](../../iosApp/iosApp/Shared/AppleDecodeCapabilities.swift), built separately from Emby's request. On Apple TV 4K, iPhone and iPad it offers direct play of H.264, HEVC, AV1, MPEG-2 and VP9 with no device resolution limit. On Apple TV HD and the simulators the request has an overall 1920×1080 ceiling and only offers the codecs VideoToolbox decodes in hardware (H.264 on Apple TV HD's A8, which has no hardware HEVC decoder) plus three software decoders, each kept within the limits Vivid's test files cover: AV1 (Main profile, up to 10-bit) and VP9 (Profile 0, 8-bit) up to 1080p at 30 fps and 3 Mbps, and MPEG-2 (Main profile, 8-bit) up to 720×480 at 31 fps and 7 Mbps. H.264 is limited to 8-bit at up to 60 fps. Anything outside those limits, including 4K, HEVC, 10-bit H.264 and PAL DVD video, is left for Jellyfin to transcode to H.264 HLS at 1080p or lower. A selected quality's resolution combines with the 1080p ceiling, and the lower one applies. If the account has `EnableVideoPlaybackTranscoding` turned off, or Jellyfin returns no transcoding URL, that title won't play on Apple TV HD. These limits are covered by request tests only; they haven't been checked on Apple TV HD hardware or against a live Jellyfin server. Vivid retains its shared controls, engine, subtitle inventory and next-episode behaviour. The player also offers text subtitle files Jellyfin keeps beside the media, and its text streams while transcoding, fetched with the account's request headers and without following redirects. The detail-page subtitle menus list the same files beside the embedded tracks, and a choice made there is applied when playback starts. A new item (or a Play from Beginning) that never reaches its first frame is retired with Jellyfin's `Failed` stop flag so it does not reset resume progress or mark a title watched. Recovery reloads, retries, seeks that reload the stream and quality or track changes of an item that has already started keep reporting its real position. From the first frame Vivid reports start, progress and stop normally with the real position, and Jellyfin's resume settings decide what is kept, as for Jellyfin's own apps: by default a play that stays under 5% resets the resume point to the start, over 90% marks the title played, and a title shorter than five minutes is marked played instead of keeping a resume point. Vivid's separate completion policy still marks a title played at 90%, at a credits marker or on a natural end. Overlapping playback starts use an attempt identity so an older Jellyfin response cannot replace a newer session. Progress reporting and retirement are serialised during Jellyfin replacement. Validation failure before retirement preserves the previous session; cancellation after retirement leaves no stopped session referenced by the bridge. PlaybackInfo uses `AutoOpenLiveStream=false`, so cancelled or superseded negotiations are discarded locally without sending a stop that could clear current server playback. The player's Stream badge on Apple TV reads each video stream's `VideoRangeType`, `DvProfile`, `DvBlSignalCompatibilityId` and `Hdr10PlusPresentFlag` to show the Dolby Vision profile (for example DV P8.1), HDR10+, HDR10 or HLG; `DOVIInvalid` streams aren't labelled as Dolby Vision. Detail pages, version pickers and Continue Watching in the Apple TV Home focus info show the same label.

Library browsing requests card metadata without cast, media sources, streams or chapters; detail and playback requests retain the full fields. Discover uses the Home field set, and Similar, which only uses item IDs, uses the browse set. Seasons, episodes and collections keep the full fields. Cast and crew route IDs map to native person IDs in one bounded dictionary per server and user, capped at 4,000 people. Older per-person defaults keys move into it on first use. Native library-ID mappings are reused for five minutes, partitioned by server, Jellyfin user and login epoch. Watched state, favourites and pagination remain in browse responses. A bounded check of two 60-title movie pages reduced response size by about 91% and measured 3.4–4.4 seconds instead of about 7 seconds; these are individual server/network observations, not an on-device performance guarantee.

Season metadata retains Jellyfin watched and unplayed counts. Jellyfin 12.2 can count every version of an episode in a season's `RecursiveItemCount` and `UnplayedItemCount`, and copies `RecursiveItemCount` into `ChildCount` when both are requested, so a season of 8 episodes with two versions each reports 16. The seasons request is paired with a light one asking for `ChildCount` alone, which Jellyfin returns with versions grouped. Only when a season's grouped count is lower does the core list the series' episodes once and recount episodes, watched and unplayed from the grouped rows of each season whose episodes have more than one version. A season detail page runs the same check for its own season before listing its episodes. Seasons without versions keep the server's counts, and a failed check or listing leaves them unchanged. Episode detail mapping retains watched flags and tick-based resume positions. Continue Watching carries the tapped episode ID through the iOS and tvOS season loader. When Jellyfin groups multiple versions under a different representative ID, the core fetches the requested episode alongside the season list and substitutes its exact ID, progress and media sources into that episode row. Earlier unwatched episodes do not override an explicit resume selection; Next Up retains the server’s ordering. On iPhone, initial episode-rail positioning does not replace Jellyfin’s requested resume episode; a user scroll can change the selected episode.

Jellyfin series discovery cards use portrait posters on iOS and tvOS, including newly added episodes or seasons. Series posters request the main series artwork rather than episode or season artwork. Continue Watching and Next Up retain the same card sizing and layout as Emby and Silo, using the episode preview image for episode cards. Episode stills remain separate for the episode lists inside detail pages.

Home refreshes Jellyfin on every foreground entry and every ten seconds after the previous refresh completes while visible on iOS and tvOS. Polling stops while Home is hidden, the app is inactive, or playback is presented. Independent Home requests run concurrently, with latest-library rows fetched in pairs in server order. Home omits cast and chapters while preserving media sources, streams and user data. Updates still depend on the Jellyfin server completing its library scan and returning current data.

Home supports a Jellyfin-specific option to combine Continue Watching and Next Up. The shared Apple TV six-row cap applies after combining rows. Spotlight presents the combined Continue Watching choice too, interleaving resume and Next Up items within its ten-slide limit. iPhone, iPad and Apple TV support eight saved server-account cards. Person IDs map to Vivid navigation IDs within the Jellyfin account, including crew. More Like This uses Jellyfin’s similar-items endpoint on iOS and tvOS.

Downloads respect the account's download permission. An account that may also transcode playback (`EnableVideoPlaybackTranscoding`) can download movies, episodes, seasons and whole series at 20, 10, 5, 2 or 1 Mbps: Vivid saves the server's playback transcode of `/Videos/{Id}/stream.mp4` (H.264 with its video bitrate capped to the chosen preset, stereo AAC on top, in MP4, up to 4K at 20 Mbps, 1080p at 10 and 5 Mbps, 720p at 2 Mbps and 480p at 1 Mbps, with embedded text subtitles saved as separate files) through the background session, so it keeps downloading with the app closed. Progress uses an estimate until the file finishes. An interrupted transfer resumes only if Apple's downloader has usable resume data, which a server can't normally offer for a transcode it's still producing, so it usually starts again. A 1 Mbps season was checked end to end against a live Jellyfin server from the iOS simulator. Download Season and Download All Episodes register each present episode with a media file in one request, skipping missing or virtual episodes and episodes already downloaded. Jellyfin's season episode lists carry every grouped version of an episode, so the series download sheet and Choose Episodes list them (for example 4K HDR and 1080p) the same way as on Silo, and choosing one registers each episode with its matching source. An episode without that version uses the server's usual file. A smaller quality is a playback transcode of the chosen source; a 4K version only offers 4K transcodes. A 1080p version and a 2 Mbps transcode of single episodes were checked against a live Jellyfin server from the iOS simulator. Downloads take their watched state from Jellyfin as well as from offline playback: when Vivid comes to the foreground and when the Downloads tab opens, it reads the played state and resume position of every downloaded item from `/Items?UserId=…&Ids=…`, so an episode watched by streaming, in Vivid or another app, shows as watched and is offered by Free up space. Progress from offline playback goes to Jellyfin at the next download sync as a playback stop report (`/Sessions/Playing/Stopped` with only `ItemId` and `PositionTicks`), which Jellyfin's source shows it accepts without a prior start (not yet checked against a live server), so its resume settings decide what is kept, as for a streamed play, rather than a direct `UserData` write that would bypass them. The report carries no `PlaySessionId`, so it can't end a transcode, and no `MediaSourceId`, so it updates the downloaded item itself. Jellyfin records the sync time as the last played date when it keeps a position or marks the title played, logs the stop in its activity log and notifies plugins such as webhooks, and a report for an item it no longer has changes nothing and is accepted, so partial progress for it leaves the queue. Offline completion still follows with the separate watched write, which keeps its queue entry until that write succeeds; retries repeat only the watched write, not a stop Jellyfin has acknowledged once Vivid has saved that acknowledgement. A stop whose answer never arrived, or whose acknowledgement wasn't saved before the app closed, stays queued and can be sent again. A stop Jellyfin refuses outright for another reason (a 4xx other than 401, 408 or 429) is reported back as an error, so it doesn't hold up the rest of the queue and leaves it after the usual retries, unless the item was watched to the end. Offline progress still waiting to be sent keeps its local state, and marking an item unwatched on the server clears it on the device. The stop report's request shape is covered by a provider test; it hasn't been checked against a live Jellyfin server. Series monitoring isn't available, so the Delete watched episodes default has no effect on Jellyfin and nothing is deleted automatically. This is covered by provider and merge tests in the iOS simulator and hasn't been checked against a live Jellyfin server. Emby Sync jobs, automatic series downloads and server administration are not implemented. Watchlists are account-scoped. Removing items from Continue Watching is a Silo feature and is not offered for Jellyfin, so Continue Watching follows the server. Optional MDBList sync reconciles watchlists and exports newly confirmed watches; eligible shared preferences sync through Vivid’s private iCloud vault. Playback/subtitle preferences and sync checkpoints remain device-local. Collection browsing is supported; collection editing and Jellyfin realtime events are not implemented. Jellyfin users are server accounts, not Silo household viewing profiles.

## Apple TV Top Shelf

Top Shelf loads Continue Watching and Next Up directly from this provider’s native endpoints, independently of the in-app combined-row setting. It preserves the exact episode ID and resume progress, uses the main series poster for episodes, and keeps the existing detail and direct-play actions. Credentials come from the selected native Apple TV user’s saved account; the account, native user and credential epoch are checked again before returning the response. Silo retains its existing Top Shelf request path. Personalised content requires a single signed-in, unprotected saved account and the existing viewing-profile policy. Multiple accounts show static Vivid artwork; account changes request a system refresh.

Focused native Top Shelf request/mapping checks and the tvOS extension build passed. A read-only Jellyfin check returned both rows and a credential-free series poster URL returned HTTP 200. Jellyfin Top Shelf presentation and interactions on the Apple TV Home Screen still need device verification. This implementation is included in the published source; TestFlight availability is tracked in App Store Connect and its beta source mappings.

## Verification

Jellyfin 12.1.0 live checks passed for authentication, library views, full catalogue fields, resume and next-up rows, latest items, filters, movie details, similar titles, seasons, episodes and PlaybackInfo negotiation. A direct-play stream returned an authenticated HTTP 206 response for a bounded 4 KiB read. These checks did not submit watched-progress changes.

- Fifteen focused Jellyfin XCTest cases and six extracted Home/Spotlight tests passed using the production provider sources and wire models in a temporary macOS harness. Host services were stubbed.
- Fifty-four deterministic lifecycle checks execute the complete production start, stop and progress methods with instrumented server/settings boundaries. They cover overlapping starts, cancellation, pending-start invalidation, progress ordering, validation failure and completion after a failed stop. Removing either production start/stop invalidation caused a runtime test failure. These checks do not exercise the media engine or real network timing.
- The [full iOS simulator test suite and tvOS simulator build](https://github.com/blurbery/vivid/actions/runs/35497384531) passed for application revision `04910755d2f6c0f22ff2b8976ba6b7eb58b074fe`, including the final review fixes. Focused playback end/recovery, early-display, auth-refresh and native-profile checks also passed.
- The signed iPhone Debug build was installed in place on iPhone 16 Pro Max, with app/extension versions, signing, provisioning and the patched media-library marker verified. After testing the integration and follow-up UI/browsing fixes, blurbery accepted it for review. The later concurrency review fixes passed automated checks but have not been installed on that phone.
- iOS/iPadOS and tvOS 0.14.3 (33) were distributed through TestFlight. Subsequent device feedback identified a multi-version Continue Watching mismatch on both platforms. The follow-up exact-episode fix passed 24 provider tests and 17 extracted request-routing assertions; a read-only live check resolved the affected episode’s exact ID, progress and audio/subtitle metadata. A missing resume version (HTTP 404 after the legacy fallback) leaves the valid season rows available without inventing resume state; authentication, cancellation, transport and server failures still propagate. These checks do not establish on-device UI performance, and do not establish a complete device matrix for the follow-up fix. Use App Store Connect’s per-build source mappings to identify the distributed revision.
- Season counts for episodes with several versions were checked read-only against a Jellyfin 12.2 server from the iOS simulator. Seasons with versions reported `RecursiveItemCount` above their episode lists (12 for 6 episodes, and 7 for 4 episodes that each report two versions, so the excess is not always a simple doubling), while `ChildCount` requested on its own matched the lists. Before the `ChildCount` check was added, the fixed seasons route and a season detail returned the episode-list counts for every season with versions, and a series without versions kept matching counts. The check itself is covered by focused provider tests and a simulator build, not a further live run. Watched counts for seasons with versions are covered by provider tests only, as no watched state was changed on the server.
- Full on-device settings coverage, saved-account switching, native Apple TV user switching, live tvOS playback and older Jellyfin server versions still need verification.


For an iOS Debug test launch, `VIVID_SHOW_SERVER_SETUP=1` opens the provider chooser before account restoration. This launch-only switch does not sign out saved accounts or reset Keychain/iCloud data. Ordinary launches retain their existing behaviour.
