<h1 align="center">Versioning &amp; Releases</h1>
<p align="center">Semantic versions. Clear release notes.</p>
<p align="center"><a href="../../README.md">Home</a> · <a href="../README.md">Documentation</a> · <a href="../../CONTRIBUTING.md">Contributing</a> · <a href="https://github.com/blurbery/vivid/releases">Releases</a></p>

---

Vivid uses `semantic-release` to publish a GitHub source release after updates reach `main`. The workflow uses a standard Ubuntu runner, has a five-minute limit, and runs the release-rule checks before publishing. Apple signing and distribution are not part of this workflow.

The largest change since the previous version determines the increment. Tags use `v0.1.0`; the release title is `0.1.0` with no prefix, product name or extra wording. The release workflow creates each `v*` tag, and the `Release tags` repository ruleset stops it being moved or deleted.

Shipped logo, branding, artwork and small visual polish updates are **patch changes**: increment the last number by one, for example `0.0.1` → `0.0.2`. Use `fix:` or `style:` as appropriate, not `feat:`. Documentation-only changes use `docs:` with `[skip release]` and must not increment the version. Reserve `feat:` for new functionality. Keep existing published versions; this policy applies to future releases.

GitHub lists Vivid’s source releases from `v0.1.0`. Tags `v0.1.0` to `v0.12.10` all point at the repository’s initial commit, so they do not identify separate source revisions; `v0.13.0` is the first release tagged on its own commit.

## Version shown in the app

Settings → About displays `CFBundleShortVersionString` and `CFBundleVersion` as version (build), with the source commit underneath. `scripts/xcode/stamp-source-revision.sh` runs as the last build phase of both app targets and records the commit as `VividSourceRevision` in the built Info.plist, adding `-modified` when tracked files had uncommitted changes (`Package.resolved` is ignored). The first row of Open Source Licences, "Source for this build", gives the same commit and its GitHub link. The Apple marketing version and GitHub source-release version are independent. Record the exact pushed source commit for each TestFlight upload; do not change the Apple marketing version to match a GitHub tag.

TestFlight marketing version stays `0.14.3` until blurbery explicitly approves changing it before archiving or uploading. Each authorised update uses that platform's latest uploaded App Store Connect build number plus exactly 1. iOS/iPadOS and tvOS advance independently, including paired uploads; never skip numbers just to make them match. App Store Connect is the current upload history. The [recorded Apple builds](#recorded-apple-builds) below are historical evidence, not a maintained upload ledger.

Apple requires TestFlight App Review for the first build of a version; later builds within that version may not need a full review. Keeping the version stable avoids introducing a new version for every beta update, but does not guarantee immediate approval. Returning to a previously reviewed marketing version does not guarantee that a new build will skip review; expiring another build does not provide that guarantee either. See [Apple’s TestFlight App Review guidance](https://developer.apple.com/help/glossary/testflight-app-review/).

Check the uploaded history before each release, including builds still processing. Local development and device-test builds do not reserve TestFlight numbers, and GitHub release versions do not control them. A single-platform update leaves the other platform's uploaded build unchanged. Every embedded extension must match its containing app. If the latest uploaded number cannot be verified or the next number is unavailable, stop and report the conflict rather than guessing, reusing or silently skipping a number. Do not assume the committed baseline has been uploaded.

`iosApp/project-common.yml` is the committed source for the Apple marketing-version and build-number baseline shared by all shippable targets. TestFlight archives must retain that approved marketing version. Its committed build numbers are an older baseline that archive-time overrides replace, so they do not show the latest upload. The tag resolver in `scripts/ci/resolve-marketing-version.sh` remains available for source-tagged unsigned builds; it must not automatically select the marketing version for TestFlight. Unsigned lanes accept `BUILD_NUMBER` as `CURRENT_PROJECT_VERSION`. Check both finished archives and their extensions before upload.

The app does not query GitHub APIs at runtime. A local or simulator build is not an uploaded TestFlight binary, even when its version and counter match. Identify distribution by the actual uploaded archive and source revision.

## TestFlight-only updates

Build, validate, upload and distribute the authorised source through App Store Connect. Use archive-time `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` overrides, verifying the app and extensions. Do not commit counters, create a bookkeeping PR/tag/release, or add an upload record solely for TestFlight. Preserve signed archives and dSYMs; clean task-created regenerable caches after acceptance.

## Release notes

### TestFlight test groups

Every user-authorised Vivid TestFlight upload includes distribution to the existing internal and external test groups for that platform, unless the user explicitly limits the audience. After processing, attach the exact uploaded build to those groups, save relevant What to Test notes, and submit for Beta App Review when required. Verify group assignment and actual availability separately; report processing, review or permission blockers as pending, never as distributed. Reuse existing groups and testers; do not create groups, invite new testers or change public-link settings without explicit permission. If the intended groups are ambiguous, ask before assigning. This standing distribution preference does not independently authorise a new upload.

### TestFlight note format

Use simple plain-text change bullets, with one blank line between them. State what was fixed or changed and its user-visible effect, using concise Australian English. Do not add headings, bold markers, testing instructions, em dashes or source links to What to Test. Describe only changes included in the build; do not invent validation results.

```text
• Fixed slow media information when opening series details.

• Fixed skip buttons appearing while playback was loading or buffering.
```

Keep exact per-platform version/build source mappings and dependency build instructions in the beta description, following [source delivery](distribution.md#licence-and-source-delivery).

This format applies to TestFlight notes only. GitHub release notes and App Store notes retain their separate writing preferences.

### GitHub release note format

Documentation-only and housekeeping commits must include `[skip release]`. Put the marker in the PR title: pull requests are squash-merged, and the PR title becomes the squash commit subject. Such commits neither trigger a release nor contribute to the version calculation or notes in a later release: the release job does not run when the pushed head commit (the squash commit) contains the marker, and the release tooling drops every commit containing it, in any letter case. A skipped app change appears in release notes only if a later releasing commit lists it in its `Release-Notes:` block. An app change can carry the marker on purpose when it should ship together with a later change; that later commit's `Release-Notes:` block must then list both. Ordinary commits retain the normal versioning rules.

Keep this format for every app release. Do not publish a release for documentation-only work. Release bullets describe user-visible changes in plain language; implementation details and testing evidence belong in the contribution report.

> [!IMPORTANT]
> Release titles contain only the version number. Bodies contain only flat update bullets, with no headings, dates, author names, commit hashes, comparison links or automated footer.

The default bullet is the commit subject with its Conventional Commit prefix removed. A squash-merge subject keeps its `(#123)` pull request suffix in that bullet, so app releases normally use curated bullets.

For an update with several user-visible changes, add curated bullets to the commit message. The squash commit body starts blank, so add the block there when merging:

```text
feat: add a new browsing feature

Release-Notes:
- Add the new browsing feature.
- Improve keyboard navigation in the picker.
- This release will be available on TestFlight soon.
```

Put `Release-Notes:` on its own line. Directly after it, start each bullet with `- ` at the beginning of the line and keep it to one line. A blank line or any other line ends the list. By convention, the releasing commit's block ends with “This release will be available on TestFlight soon.” The release tooling doesn't add it: it joins the bullets of every releasing commit in the release and keeps only the first copy of a repeated bullet. Each push to `main` normally releases one commit, so put it in that commit's block; when changes are batched with `[skip release]`, list them all in the final commit's block and end it with this bullet. Write specific changes in plain language; do not describe planned integrations as delivered. Internal commit bodies and AI attribution trailers are not copied into release notes.

## Validation

```sh
npm ci --ignore-scripts --no-audit --no-fund
npm run test:release
```

The tests cover major/minor/patch rules, ordinary commit messages, empty ranges, `[skip release]` exclusions, curated bullets, duplicate notes, markup escaping and the version-only title. They validate release tooling, not the Apple app. For app changes, report relevant builds, tests, device checks and gaps under the contribution policy; blurbery controls publishing and merge decisions.

Dependencies are pinned in `package-lock.json` and need Node.js 24.10 or later (the workflow uses 24.15.0); the Node tools do not become app dependencies; Dependabot proposes updates to them once a month. The `VIVID_GIT_NOREPLY_EMAIL` repository variable must hold `blurbery`'s GitHub noreply address. The workflow uses its scoped `GITHUB_TOKEN` and does not publish an npm package or comment on issues/PRs.

Each workflow in `.github/workflows/` on main has its own triggers. The source-release workflow runs on pushes to main and on manual request. Player regression runs on every pull request, on manual request and on pushes to main that change anything under `iosApp/` or `scripts/xcode/` (the app targets' build phases), its check scripts or the workflow. On a pull request its `changes` job first checks for changes to those same files and skips the build and test jobs when there are none, building everything when it can't compare the pull request with its base commit; its `Player regression result` job always runs and fails when any other job failed or was cancelled, and a skipped job counts as passed. Pull requests that change those files run the complete iOS suite as a normal Debug build, plus the `VividTVTests` suite on a tvOS simulator unless every changed app file is iOS-only (the iOS spec, `iosApp/DownloadsActivity/`, the iOS entitlements and signing files, and tests outside `VividTVTests`; source in `iOS/` folders still counts, because the tvOS target compiles it); docs, the check scripts and other files outside the app don't count towards the tvOS suite, but `scripts/xcode/` and the workflow itself do. Pull requests that can't be compared with their base commit run the iOS suite, the tvOS suite and the device builds. After a merge to main that changes those files, player regression runs the complete iOS suite only as a build compiled with the Release optimiser (`-O`, whole-module), with no Debug or tvOS suite, because some faults only appear in optimised TestFlight and App Store builds. Manual runs can add the optimised build with the `optimised` input. Each iOS test run also checks the adapter's track ID translation and teardown (`scripts/tests/mpv-track-tests.py`); the tvOS job does not run that check. Each iOS job, except a `baseline_ref` comparison run, also checks that both apps pin the Lucid Engine package (`scripts/ci/check-engine-package-pin.py`) and that no tracked file names the previous third-party player code or engine package (`scripts/ci/check-no-previous-player-code.py`). Player regression's iOS test runs also run `scripts/ci/check-introdb-client.sh` and `scripts/ci/check-mdblist-sync.sh`, and Claude Code Review runs `scripts/ci/claude-review.py`. No workflow runs `scripts/ci/check-seerr-client.sh`, `scripts/ci/check-tmdb-client.sh`, `scripts/ci/check-tv-remote-wheel.sh` or `scripts/ci/resolve-platform.sh`; PR checks runs both resolvers' tests, and the sideload workflow runs `scripts/ci/resolve-marketing-version.sh`. Player code checks (`player-code-checks.yml`) runs those two checks again on every pull request and every push to main, whatever it changes, on a standard Ubuntu runner, because player regression only builds for app changes. When a pull request or push changes a project spec or `Package.resolved` (where the engine pins live), or can't be compared with its base commit, player regression also builds both apps unsigned in the Release configuration for generic iOS and tvOS devices; manual runs add those builds with the `device_builds` input. Before a TestFlight upload, confirm an optimised run passed for the uploaded source: the main run after the last merge that changed the app (a merge that changes none of those files starts no run), or a manual run with `optimised` for a branch build. Lucid Engine build (`lucid-engine.yml`) builds every engine library from upstream source with Vivid's patches and runs the engine's host tests on GitHub's public `macos-26` runners whenever `engine/` or the workflow changes, on pushes to main and to the engine's `experiment/lucid-engine-*` branches and on pull requests. It starts on every pull request: a `changes` job on a standard Ubuntu runner skips the macOS jobs unless `engine/` or the workflow changed, or it can't compare the pull request with its base commit, and its `Lucid Engine result` job always runs and fails when any other job failed or was cancelled; see the [Lucid Engine build guide](../cores/lucid-engine-build.md). It publishes nothing. A Lucid Engine package release (`blurbery/lucid-engine`) is a separate, explicitly authorised step: `engine/publish_package.py` prepares it from one green run, and the app's pin in both project specs and `Package.resolved` then moves in its own change ([Publishing the package](../cores/lucid-engine-build.md#publishing-the-package)). Engine releases have their own version numbers and do not follow the app's semantic-release versions or TestFlight build numbers. Claude Code Review (`claude-code-review.yml`) comments on pull requests from branches in this repository, skipping drafts, bot pull requests and Markdown-only changes, and does nothing without its API key; a manual run is a dry-run benchmark that posts nothing. Sideload IPA Build (`sideload-ipa.yml`) is described in [App Distribution](distribution.md#github-and-unsigned-sideload-builds). Sideload publishing remains a separate, explicitly requested action and its legacy publishing format needs review before use. Do not enable paid capacity or change distribution settings as part of an ordinary source release. See [App Distribution](distribution.md).

PR checks (`pr-checks.yml`) runs on every pull request, and again whenever its title or description is edited, it moves between draft and ready, or a label is added or removed, on standard Ubuntu runners. `scripts/ci/check-pr.py` checks that the title is a Conventional Commit; that a PR changing nothing shipped in the app (nothing under `iosApp/` outside `iosApp/Tests/`, and nothing under `scripts/xcode/`, which holds the app targets' build phases) has `[skip release]` in its title; that a branch in this repository is named `<type>/<short-description>` (with `release/`, `experiment/` and GitHub's own `revert-<number>-` branches also allowed); and that the description completes every section of the PR template, with the documentation box ticked. Draft PRs get warnings for the description until they are marked ready, branches in forks are not checked, and bot PRs such as Dependabot's skip the branch and description checks but not the title check. When the release tooling, the release or sideload workflow, the diagnostics relay, the sideload resolvers, the PR, docs or action pin checker, the PR template or this workflow change, the workflow also runs `npm run test:release`, `npm run test:relay`, the resolver tests in `scripts/ci/`, `scripts/tests/check-pr-tests.py`, `scripts/tests/check-docs-tests.py` and `scripts/tests/check-action-pins-tests.py`, so they pass before merge; the release workflow runs only the release tests, and only after merge. Its `PR checks result` job always runs and fails when any of its other jobs failed or was cancelled. Its checking jobs skip closed PRs, where the result job still runs and passes. Editing a title or description, or adding or removing a label, doesn't change the commit, and the result job only reports once the jobs it waits for finish, so branch protection also requires the `PR title, branch and description` and `Docs` jobs, which report as soon as the run starts; a merge then waits until the edit or label change is checked.

Dependabot (`.github/dependabot.yml`) proposes updates once a month for the workflow actions and the npm release tooling, each at least a week old: minor and patch updates in one pull request per ecosystem, and major updates in another. It also opens security fixes, including for the sideload lanes' Ruby gems, which get no routine updates. Swift packages get no version updates: the Lucid Engine pin and the other app packages move by hand with their notices, and Dependabot alerts still cover them. The Actions, npm and Ruby pull requests change nothing that ships in the app, so their titles start with `[skip release]` after the type (for example `ci: [skip release] bump the actions group with 2 updates`) and they get the `docs-not-needed` label. As with any change to those workflows, an Actions update that touches `player-regression.yml` runs its iOS and Apple TV suites, and one that touches `lucid-engine.yml` runs the engine's macOS jobs; most touch both, since both use checkout and upload-artifact. The `Action pins` job in PR checks runs `scripts/ci/check-action-pins.py`, which parses each workflow as YAML (with Ruby, which GitHub's runners include) and fails any job or step `uses:` that names a tag or branch rather than a full commit SHA, or whose line has no trailing version comment; local `./` actions and `docker://` images aren't checked. Dependabot updates the version comment with the SHA.

Branch protection on `main` requires a pull request and these checks from GitHub Actions: `PR checks result`, `PR title, branch and description`, `Docs`, `No previous player code, engine pin`, `Player regression result` and `Lucid Engine result`. Every workflow behind them starts on every pull request, and a job skipped because nothing it covers changed counts as passed. The branch doesn't need to be up to date with `main`. Linear history is required, conversations must be resolved before merging, new commits dismiss earlier approvals, and no approving review is needed. Administrators aren't held to these rules, so blurbery can merge past a failing check in an emergency. Workflow runs on pull requests from outside contributors' forks wait for blurbery's approval, so their checks stay pending until then. Changing a pull request's base branch, by hand or when GitHub retargets it after the old base branch is deleted, doesn't run player code checks, player regression or Lucid Engine build again, so push a commit, or close and reopen the pull request, after retargeting it.

The `Docs` job in PR checks runs `scripts/ci/check-docs.py` and `scripts/tests/licence-texts-tests.py` on every pull request. It fails when a tracked Markdown file has a relative link or image whose file or folder isn't in the repository, or a `#` anchor into a Markdown file with no matching heading or id, unless the base branch already had that broken link, which is only reported (the links are counted, so another copy of an already broken link still fails); when a doc still names, in inline code, a repository path the PR removes or renames, on a line the PR doesn't touch; when a line the PR adds or rewrites names, in inline code, a path that doesn't exist, unless the PR itself removed it, a doc already named that missing path before the PR, or the line reads as history (for example "the previous script, now removed"); when a line the PR adds to a Markdown or HTML file or an issue template has an em dash; when the PR changes an area in the table below without changing its doc; when a doc, trigger or exclude in the map matches no tracked file; and when the licence texts no longer rebuild. Only paths inside a top-level folder are checked, and paths with wildcards or placeholders, and paths Git ignores outside `docs/`, are skipped. External links aren't fetched. When a mapped change really needs no doc update, say why under **Documentation impact**; blurbery can then add the `docs-not-needed` label, which skips the table's rules but not the check that the map's paths exist. Only people with triage access or above can add labels; Dependabot's pull requests get the label from `.github/dependabot.yml`, because a version bump doesn't change what the docs describe.
